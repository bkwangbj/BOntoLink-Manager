## 一、演示数据污染生产功能（最严重的设计问题）

这是当前功能设计最大的隐患：**mock 数据与真实数据在同一接口中混合返回，用户无法区分**。

| # | 问题 | 证据 |
|---|------|------|
| 1 | **图谱接口向生产响应注入虚构关系**：`/api/graph/ontology` 在真实边不足时调用 `ensureMockRelations`，用 `Random(42)` 随机编造 eq（等价）/dis（互斥）/union（并集）/link 五类假关系边，目标"整图至少 60 条边"。用户在本体图谱里看到的语义关系可能是根本不存在的 | `GraphController.java:124, 187-213`（已验证） |
| 2 | **实例探索全部数据为内存伪造**：`/api/instance/*` 全部走 `InstanceMockService` 随机生成实例池。"物理数据源绑定"配得再认真，实例查询也不读真实表——绑定绑了个寂寞 | `InstanceController.java:23`、`InstanceMockService.java:14-21` |
| 3 | **对象图谱 Tab 全量假数据**：无论选哪个对象类型，都渲染同一份"水文测站"七大维度 mock | `TabObjectGraph.vue:192-262` |
| 4 | **时序图表/事件时间轴为合成演示数据**，代码注释自述"演示用" | `TimeseriesChart.vue:6`、`EventTimeline.vue:7` |
| 5 | **AI 助手纯 setTimeout 假对话**：固定文案"（演示数据，后续接入推理引擎）"；AiFab 悬浮按钮被注释隐藏、对象抽屉"AI 助手"按钮只 toast"待联调"——需求中的 AI 三处触点（侧栏/悬浮球/对象详情）全是摆设 | `AiAssistant.vue:37-39`（已验证）、`App.vue:13`、`ObjectTypes.vue:1224-1226` |
| 6 | **新建向导内置 mock 物理表兜底**：无后端时静默使用假表清单，用户以为配了真实映射 | `NewObjectTypeWizard.vue:328` |
| 7 | **语义扩充查询演示结果 mock**：分词器演示返回固定示例拆分结果 | `lib/analyzers.js:77` |

**设计建议**：引入全局"演示模式"开关（如 `bontolink.demo-mode`），mock 注入只在开关开启时生效，且前端对演示数据统一加水印/徽标。当前默认行为等于" silently 说谎"。

## 四、信息架构问题

1. **全局"领域"选择器是纯摆设**：侧栏顶部最高优先级的 `selectedDomains`，**没有任何页面读取**。各页面（ObjectTypes/Discover/Instances）各自再造本地筛选，用户在一个页面选好的上下文到下一页就丢。
2. **孤岛路由**：`/workspace/maker` 可视化制作有路由无入口（菜单被注释、唯一跳转函数未被模板调用），只能手输 URL 进入。
3. **重复建设**：图谱三套（Graph.vue 1311 行死代码 / GraphG6.vue 现役 / GroupGraph.vue）、图表两套（MakerEmbed + InstanceCharts 死代码）、属性画布双版本、全局搜索三种行为。死代码文件共 5 个（Graph.vue、InstanceCharts.vue、TabPropsCanvas.vue、LeftGroupTree.vue、AiFab.vue）。
4. **路由分组与目录归属错位**：值类型/枚举类型在"资源"菜单组，组件却在 `views/config/` 下。
5. **对象抽屉信息过载**：15 个 Tab 中 3 个占位、1 个全 mock、1 个假按钮，真实可用约一半。
6. **主题系统失效**：选"跟随系统"刷新后恒为浅色（`data-theme="system"` 无 CSS 分支），且系统切换深浅色页面不联动。

## 五、API 与业务逻辑设计问题

### API 一致性
- **URL 三套体系**：单数（`/api/category`）/ 复数 kebab（`/api/link-types`）/ 缩写（`/api/tc-bind`）混用；同一对象类型有 4 个路径族入口（`/api/resource/classes`、`/api/instance/object-types`、`/api/class-meta/classes`）
- **状态变更四种动词**：`POST /toggle`（非幂等翻转）、`PUT /status`、`POST /status`、`POST /deprecate`
- **统一响应分裂**：admin 成功码 0、ontology 成功码 200；404 语义五种写法（`R.ok(null)`、空 Map、空对象、`R.error(404)`、直接 500）；"删除被阻止"两种约定（400 错误 vs `R.ok({blocked:true})` 成功包装藏失败）
- **分页整体缺失**：唯一分页接口是内存 mock 分页；列表全量返回

### 业务规则漏洞
- **"有下级禁止删除"可被 update 绕过**：update 允许任意改 parent_id/category_type/code，无环检测（可把自己的祖先挂到自己下面），层级规则只在 create 校验；改 code 后子表引用全部悬空
- **两套删除入口行为矛盾**：`/api/group/{id}` 注释宣称级联实则不级联（子分组悬空），`/api/category/{id}` 反而级联——删除结果取决于走哪个端点
- **级联删除漏表**：对象类删除清 9 张表但漏 tc-bind/property_format/explore_design 等 5 张；枚举删除零级联（注释谎称"由 Mapper/数据库负责"）；数据源删除不查 `ont_class_ds` 引用
- **先删后写无事务**：链接类型 mappings、枚举 level_rules 等多处 `delete → 逐条 insert` 无 `@Transactional`，中途失败数据全丢
- **唯一性靠代码预检不靠库**：TOCTOU 并发下双双插入（SharedProperty/LinkType code）；`ont_class_property` 无 `UNIQUE(class_id, api_name)`
- **is_required 语义反转**：`ont_interface_property`（0=Required）与 `ont_class_property`（0=非必填）语义相反，新增接口属性默认变 Required，疑似埋雷

### 数据模型
- **四套标识并存**：id / rid / api_name / code 混用，父子引用有的用 id 有的用 code；rid 出现双前缀拼接（`ri.ont.class.` + `class-<uuid>`）
- **双链接模型互不同步（核心缺陷）**：图谱和实例探索读旧表 `ont_class_link`（无任何 INSERT API，只有 20 行种子），CRUD 写新表 `ont_link_types`——**通过界面创建的链接类型永远不会出现在图谱里**
- **枚举体系四套并存**：`ont_enum_types` / `ont_value_types` / `ont_dic_type_class` / `ont_dict_def` 四块无统一治理
- **JSON-in-TEXT 17 处**：不可查询不可校验，解析逻辑在 Controller 手工重复
- **无外键无软删除**：与命名空间版本快照/回滚的设计目标自相矛盾

## 六、架构设计的功能性代价

1. **ontology 服务是死服务**：pom 宣称"OWL 推理/SPARQL/SQL 生成"，实际只有 3 个端点；Jena 零使用；前端零调用；且模块内无数据源配置、包扫描不覆盖 data 层——**按现状根本无法启动连库**。双服务架构的成本付了（双端口/双 context-path/共享 SQLite 文件竞争/跨服务缓存失效无解），收益为零。
2. **语义扩充的写读分布与 PG 方言缺口（测试阶段状态）**：CRUD 在 admin（8088）、消费在 ontology（8089）、前端暂无入口；PG 部署下 7 张语义表不存在（迁移脚本只在 sqlite 目录）。因该模块属在测新功能，上述属于测试期未完成项：前端入口、PG 迁移脚本、admin/ontology 调用链对齐待补齐，**不是既有设计的缺陷**，待稳定后补文档。
3. **双库方言行为分裂**：PG profile 的 flyway.locations 被覆盖为不含 common → PG 下无种子数据、无语义表，与 SQLite 是"两个系统"。
4. **SQLite 单连接池**（`maximum-pool-size: 1`）全站写串行化，"连外部库拉数+写本库"类操作有阻塞全站风险。

## 八、整改优先级（按 ROI）

| 序 | 事项 | 理由 |
|----|------|------|
| 1 | 加 demo-mode 开关，隔离全部 mock 注入（图谱/实例/向导/AI） | 半天工作量，消除"系统对用户说谎"的最大信任风险 |
| 2 | 修死链 + 404 路由 + 打通 selectedDomains 全局筛选 | 小改动全局受益 |
| 3 | 合并 `ont_class_link` / `ont_link_types` 双模型 | 不修则"建的链接不进图谱"的核心功能断裂永远存在 |
| 4 | 决策 ontology 服务去留：补数据源配置真正启用，或把 3 个端点并回 admin 下线 8089 | 当前是纯成本零收益 |
| 5 | 统一删除策略（引用检查清单 + 级联补漏 + 事务） | 数据完整性地基 |
| 6 | 假按钮要么接真实能力要么下线；向导步骤条与实际流程对齐 | 演示可信度 |
| 7 | 需求侧：确认基准版本（260521）、归档旧版、给语义扩充补需求或下线 | 避免继续无据开发 |
